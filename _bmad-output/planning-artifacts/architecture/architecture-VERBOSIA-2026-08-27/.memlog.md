- (decision by user) Repository-versioned files are the canonical source of truth for Brand Memory and Evidence Ledger. Derived indexes are disposable and rebuildable. Mutations require an explicit draft -> validate -> approve -> apply workflow.
- (decision by user) Use hybrid repository storage: .verbosia/brand/brand-memory.json as the canonical versioned Brand Memory document; .verbosia/evidence/<evidence-id>.json as immutable evidence records. Corrections append a new record using supersedes. Any indexes are derived and rebuildable.
- (decision by user) Model Claim as a first-class entity between Brand Memory and Evidence Ledger. Brand Memory controls communication authorization; claims have stable IDs, lifecycle status, and evidence references. Evidence never auto-approves a claim. Public use requires an approved claim with current evidence applicable to the requested locale, market, and context; otherwise block or request human review.
- (decision by user) Resolve Brand Memory context through deterministic overlays: global base -> locale -> geographic market -> channel/audience context. Locale, market, channel, and audience remain distinct dimensions. Overlays may adapt tone, terminology, CTA, and examples but cannot change facts, numbers, or promises without an approved Claim and applicable evidence. Keep initial overlays inside brand-memory.json.
- (decision by user) Govern evidence through explicit dimensions rather than an opaque confidence score: provenance, permission, support role, applicable scope, temporal validity, and sensitivity. Market signals cannot independently validate factual promises; inferences remain labeled and require human approval; restricted evidence may support a claim without exposing its contents; expired evidence invalidates dependent use; validation explains failed dimensions.
- (decision by user) Use a hybrid claim-validation architecture: semantic analysis may extract claims and suggest matches, but only a deterministic policy core may authorize use. Outcomes are allow, allow_with_constraints, review_required, or block, with stable reason codes and auditable references. Unknown or ambiguous claims require review. V1 remains provider-independent and local, accepting explicit claim IDs or candidates; semantic providers are optional adapters.
- (decision by user) Place Brand Memory, Evidence Ledger, claim policy, and contextual resolution in @verbosia/core. Keep @verbosia/mcp as a thin transport and presentation adapter. The local filesystem adapter implements canonical repository storage; future storage adapters may replace it without changing domain rules. No database or external service is required for V1.
- (decision by user) Separate persisted editorial lifecycle from runtime evidentiary support. Claims persist only draft, approved, suspended, or retired, with approval actor/date and optional review due date. Do not persist supported status; compute it for every validation from current evidence validity, scope, permission, and supersession. Evidence effective state is likewise derived as active, future, expired, or superseded without rewriting history.
- (decision by user) Keep the V1 MCP surface read-only with verbosia.inspect_brand_context and verbosia.validate_claims. Operate only within the authorized server root; never expose raw Evidence Ledger content; sanitize restricted evidence metadata; use stable versioned JSON outputs. Defer localize_with_context and any MCP mutation/approval tools to later phases.

- (decision by user) Adopt a portable schema-first contract using JSON Schema Draft 2020-12 for canonical Brand Memory and Evidence Ledger structures. Every canonical document declares schemaVersion. - (decision by user) Apply evidence data minimization: persist source descriptor, locator, capture time, digest, permission, scope, validity, and only an optional minimal sanitized excerpt. Keep authorized first-party artifacts at referenced in-root paths. Do not archive full third-party reviews/comments. Reject unnecessary personal data, secrets, and tokens. V1 never fetches URLs or reads outside the authorized root. Unavailable evidence requiring reverification yields review_required.
- (decision by user) Use stable referential identities: human-managed readable claim IDs; tool-generated opaque immutable evidence IDs; all references by ID, never array position or claim text. Evidence filename must match evidenceId. Claim wording changes preserve claimId; evidence corrections create a new ID and supersedes link. Reject duplicate IDs, dangling references, and supersession cycles. Compute and expose SHA-256 digests for resolved memory state to support reproducibility.
- (decision by user) Use fail-closed validation with dependency-level isolation. Invalid Brand Memory prevents context resolution. Invalid evidence is quarantined and cannot authorize use; dependent claims become review_required or block while independent claims continue. Global violations such as unsafe root, incompatible schema version, or duplicate IDs fail the operation. Unused expired evidence produces warnings. Diagnostics use stable codes, severity, file, JSON Pointer, and remediation; never treat malformed state as empty memory.
- (decision by user) Keep client-specific Brand Memory separate from future open community Context Packs for language, SEO, GEO, market, and scenario guidance. Packs are declarative, schema-validated, versioned, scoped, sourced, evidenced, tested, and classified as required or recommended; they contain no client data, cannot approve brand claims, cannot weaken governance, and execute no code. V1 defines only the composition seam; registry/catalog follows later.

Do not treat a single successful demo as sufficient acceptance.
