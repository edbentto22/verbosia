- (capability) CAP-4 — intent: An application can submit candidate Claims and receive an explainable authorization outcome. success: each candidate receives exactly one ordered allow, allow_with_constraints, review_required, or block result plus a deterministic aggregate outcome using the adopted PolicyDecisionTable and closed reason codes.

- (capability) CAP-6 — intent: Node, PHP/WordPress, CLI, and future adapters can consume portable Brand Memory, evidence, policy, diagnostic, validation, resolved-context, and Context Pack contracts. success: versioned JSON Schemas and Core contract exports are package-resolvable, offline, mechanically aligned with types, and pass shared fixtures.
- (capability) CAP-7 — intent: A policy owner can define, test, calibrate, and audit PolicyRules and approved overrides. success: rules and overrides carry the adopted identity, scope, evidence, severity, approval, expiry, and most-restrictive-wins semantics; intrinsic guardrails remain non-overridable and editorial blocking requires measured human agreement.
- (capability) CAP-8 — intent: An operator can reproduce and audit a bounded local validation decision. success: stable snapshot collection, JCS/SHA-256 state and decision digests, server evaluation time, resource limits, and deterministic ordering produce the same decision for the same authoritative inputs or a stable failure when state changes.
- (capability) CAP-9 — intent: Community integrations can target a declarative provider-neutral ContextPackContribution contract without accessing client Brand Memory. success: the schema is published and testable while V1 never loads, executes, catalogs, or lets a pack approve Claims or weaken governance.
